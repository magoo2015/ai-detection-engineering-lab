# Architecture

## Project Objective

The AI Detection Engineering Lab is a hands-on security engineering project designed to build practical experience with detection engineering, Linux security, detection-as-code, testing, CI/CD, event correlation, and eventually AI-assisted security analysis.

The project is intentionally designed around a lightweight architecture that can operate on a single DigitalOcean VPS rather than relying on a traditional resource-heavy SIEM platform. The initial focus is building and understanding the core detection pipeline before introducing AI.

The initial lifecycle is:

```text
Threat Behavior
      ↓
Telemetry
      ↓
Normalization
      ↓
Detection
      ↓
Detection Testing
      ↓
Alert Generation
```

As the project matures, the pipeline will expand to include correlation, CI/CD, MITRE ATT&CK mapping, detection tuning, and AI-assisted investigation.

## Initial Threat Scenario

The first threat scenario is suspicious SSH authentication activity against the Linux VPS.

The initial use case focuses on identifying repeated SSH authentication failures that could indicate brute-force activity. However, authentication attacks may exhibit different behaviors, so the project will avoid relying on a single rule to identify every possible SSH attack.

Examples of behaviors that may eventually require separate detections include:

* High-volume SSH authentication failures over a short period.
* Authentication attempts against multiple usernames from the same source.
* Low-and-slow authentication attempts designed to remain below simple thresholds.
* Authentication failures followed by a successful login.
* Suspicious activity occurring after a successful SSH authentication.

A detection represents suspicious behavior requiring investigation and does not, by itself, prove that a security incident has occurred.

## Telemetry Requirements

SSH authentication events originate from the OpenSSH server (`sshd`). The Linux logging system records the events generated by the service, providing telemetry that can later be collected and normalized by the detection pipeline.

Based on the initial SSH threat scenario, useful fields are expected to include:

```text
timestamp
host
source_ip
destination_ip
username
authentication_result
authentication_method
event_type
```

Both failed and successful authentication events are important.

Failed authentication events provide visibility into attempted access, while successful authentication events can provide additional context. For example, repeated failures followed by a successful authentication from the same source may represent a higher-confidence security event.

Additional telemetry may eventually be required to understand activity occurring after authentication, including sudo usage, user creation, file downloads, persistence activity, suspicious process execution, and other Linux security events.

## Detection Strategy

The project will use behavioral detection rather than attempting to classify malicious activity solely from individual log events.

The initial SSH detection strategy will evaluate multiple characteristics of authentication activity, including:

* Number of authentication failures.
* Time window in which failures occur.
* Source IP address.
* Destination host or IP address.
* Username targeted.
* Number of unique usernames attempted.
* Successful authentication following failures.
* Historical activity associated with the source.

An initial high-rate brute-force hypothesis considered during design was:

```text
15 SSH authentication failures
from the same source IP
against the same destination
within 10 minutes
```

This behavior could indicate high-rate SSH brute-force activity, but the threshold alone does not prove malicious intent.

Legitimate activity such as stale automation credentials, vulnerability scanning, or user authentication problems could produce similar behavior.

The project will therefore consider false positives and false negatives when detections are developed and tested.

### Multiple Detection Behaviors

Rather than building one large SSH rule intended to identify every authentication attack, related behaviors may be implemented as separate detections.

Conceptually:

```text
High-rate failures
        ↓
Possible SSH brute force

Multiple usernames attempted
        ↓
Possible account probing

Failures over an extended period
        ↓
Possible low-and-slow authentication attack

Repeated failures
        +
Successful authentication
        ↓
Possible account compromise
```

These detections may eventually feed a correlation layer capable of producing higher-confidence security incidents.

## Initial Architecture

The project begins with the Linux host itself as both the protected system and the initial telemetry source.

The initial architecture is:

```text
External Activity
       ↓
DigitalOcean VPS
       ↓
OpenSSH / sshd
       ↓
Linux Authentication Events
       ↓
systemd-journald
       ↓
Telemetry Collection
       ↓
Event Normalization
       ↓
Detection Engine
       ↓
Security Alerts
```

The normalization layer will eventually convert raw Linux events into a consistent security-event schema that detection logic can evaluate without depending directly on raw log formatting.

The architecture is expected to evolve toward:

```text
Threat Activity
       ↓
Linux Security Telemetry
       ↓
Collection
       ↓
Normalization
       ↓
Detection-as-Code
       ↓
Detection Testing
       ↓
Alert Generation
       ↓
Event Correlation
       ↓
Higher-Confidence Incident
       ↓
AI-Assisted Investigation
```

AI will intentionally be introduced only after the underlying telemetry, normalization, detection, and testing pipeline works and is understood.

## Current Infrastructure Security Baseline

The initial DigitalOcean VPS uses Ubuntu 24.04 LTS and has been configured with a basic security baseline before application development begins.

Controls implemented and verified include:

* Dedicated non-root `sysadmin` administrative account.
* Administrative privilege escalation through `sudo`.
* SSH public-key authentication.
* SSH password authentication disabled.
* Direct SSH login as `root` disabled.
* UFW host firewall enabled.
* Default-deny policy for inbound traffic.
* OpenSSH explicitly permitted through the firewall.
* Operating system security updates installed.
* Updated Linux kernel installed and verified after reboot.
* Ubuntu unattended upgrade service enabled.
* APT automatic update timers enabled.

Security controls are validated after implementation rather than assumed to work based solely on configuration changes.

## Engineering Principles

The architecture will follow several principles throughout development:

1. **Learning over speed** — Components should be understood before additional complexity is introduced.
2. **Detection quality over detection quantity** — A small number of well-understood and tested detections is preferred over a large rule collection.
3. **Telemetry before detection** — Detection logic should be based on an understanding of the underlying events.
4. **Testing before trust** — Security controls and detections should be validated with positive and negative testing.
5. **Correlation over isolated alerts** — Related security events should eventually contribute to higher-confidence incidents.
6. **AI as augmentation** — AI should assist investigation and detection engineering rather than replace the underlying engineering process.
7. **Cost-conscious architecture** — New infrastructure and technologies should be introduced only when they solve a real project requirement.
